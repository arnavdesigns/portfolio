Case Study — 02

Sonic — Music Visualizer

An interactive, audio-reactive visualizer that turns any track you play into live generative motion — built to explore real-time feedback as an interaction design problem, not just a screen design one.

RoleDesigner & Builder
Duration~1 Week
ToolsWeb Audio API, Canvas, JavaScript
TypeSelf-directed
01 / Overview

Problem

Most of my earlier work — like the Spotify redesign — was about screens: layouts, flows, static states. I wanted to try something where the interface has no fixed state at all, where every frame is a direct response to input (in this case, audio) instead of a click. That's a different kind of interaction design problem, and I hadn't tackled it before.

Goal

Build a visualizer that reacts to real audio in real time, with more than one way of "seeing" the sound — so the project is also about designing distinct interaction states, not just one visual effect.

02 / Research & Learning

Starting from zero

I hadn't used the Web Audio API or Canvas before this project, so a good chunk of the week was just learning how audio analysis actually works — frequency data vs. time-domain data, what an FFT size does, and how to turn raw byte arrays into something visual.

Key Observations

  • 01
    Data ≠ designGetting frequency numbers out of the AnalyserNode was the easy part — deciding what those numbers should *look* like took far longer.
  • 02
    One mode isn't enoughA single visual style got boring fast. Different music (bass-heavy vs. quiet) needed different ways of being shown.
  • 03
    Empty states matter here tooBefore any track is loaded, a blank black box feels broken. The tool needed to feel alive even with nothing playing.
03 / Design Goals

What I wanted each mode to do

Bars A familiar equalizer feel — direct, readable, satisfying to watch bounce with the beat.
Radial Waveform A calmer, more organic read of the sound — the raw waveform bent into a circle instead of a line.
Particle Field The most abstract mode — bass pulls particles inward, treble scatters them outward. Less literal, more atmosphere.
04 / How It Works

Under the hood

The audio file is read entirely client-side — nothing gets uploaded anywhere. An AnalyserNode taps into the track and outputs two kinds of data every frame: frequency data (how loud each pitch range is) and time-domain data (the raw waveform shape). Each visual mode reads one or both of those arrays and redraws the canvas roughly 60 times a second.

When no track is loaded, the same drawing functions run on a synthetic signal instead of real audio, so the tool never just sits there looking dead — it was actually a nice constraint, since it forced the empty state to be part of the design instead of an afterthought.

05 / Reflection

What I learned

This was my first time working with real-time data instead of static screens, and it changed how I think about interaction design a bit — a lot of the "design" happened in code, tuning how quickly colors shift or how strongly particles react, not in Figma. It also felt like a natural warm-up before moving into Unity, since a lot of the same instincts (frame loops, responding to input continuously, tuning how things *feel* moment to moment) carry over directly.

Key Takeaways

  • First project working with real-time, continuous data instead of static states
  • Learned the basics of the Web Audio API and Canvas rendering
  • Designed three distinct interaction modes instead of one fixed look
  • Treated the empty/idle state as a real design decision, not a placeholder
